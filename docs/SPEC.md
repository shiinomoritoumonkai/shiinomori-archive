# 思惟の森の会 資料アーカイブサイト — 実装指示書（Claude Code 用）
### 方式：GitHub Pages（静的サイト）＋ Google Drive のフォルダ階層をそのまま読み込む

> **使い方**：このファイルをリポジトリに `docs/SPEC.md` として置き、Claude Code に「docs/SPEC.md を読んで §0 のとおりに進めて」と伝える。あわせて次を置く。
> - `docs/reference/timeline-wireframe.html`：年表の配置と寸法の基準（自作のワイヤー。コミットしてよい）
> - `local/reference/`：年表の参照デザイン（§8）の画像を、自分で保存したもの
> - `local/mock.html`：MTG 用モック（マップの操作感の参考）
>
> `local/` の中身は他者の著作物（参照デザイン、村の観光マップ）を含むので、**公開リポジトリにはコミットしない**（`local/` は `.gitignore`）。

## 0. 進め方（Claude Code への指示）

1. この文書を最後まで読む。`docs/reference/timeline-wireframe.html` は実際に開き、PC の幅とスマホの幅で見る。`local/` に参照デザインの画像やモックがあれば、それも見る。そのうえで **§13 の「必ず聞く」項目だけ**を私に質問する。ほかは本文の既定値で進める。
2. マイルストーン（§11）ごとの成果物と検証方法をまとめた計画を示し、私の OK を待つ。
3. 最初に `CLAUDE.md` と `docs/PROGRESS.md` を作る。
   - `CLAUDE.md` は短く保つ：開発・テスト・ビルドのコマンド、§3.4「守ること」、進捗ファイルの場所だけを書く。
   - `docs/PROGRESS.md` には、終わったこと・次にやること・決めたことを書く。セッションが変わっても、これと本書を読めば再開できる状態を保つ。
4. M0 → M5 の順に進める。**M0 と M1 の終わりでは必ず止まり、結果を報告して私の返事を待つ。** M2 以降は、完了条件を自分で検証できたら次へ進んでよい。完了条件を満たせない事情（仕様の矛盾、Drive 側の制限など）が出たら、回避策を作り込む前に止まって相談する。
5. 「できた」と報告するときは、§10 の検証を実際に走らせ、実行したコマンドとその出力、画面のスクリーンショットを添える。検証していないものは「未検証」と書く。
6. 細部（コンポーネントの分け方、ファイル名、ライブラリの細かな選定）は任せる。ただし §3.4「守ること」、§4 のフォルダ規則、§6 のデータ形式、§7.3 の年表の構成を変えたくなったら、先に相談する。
7. 依存パッケージは最小限にし、着手時点の安定版を lockfile で固定する。TypeScript は strict。論理的なまとまりごとに小さくコミットする。

## 1. 何を作るか

早稲田大学のサークル「思惟の森の会」（岩手県田野畑村で 1966 年から育林と地域交流を続けている）の、過去 60 年分の写真を、会員・OB/OG・村の関係者で共有するサイト。公式サイト（https://moriwaseda.wixsite.com/morinokai）とは別に立て、公式サイトからリンクする。作るのも運用するのも私 1 人。

画面は 2 つ。どちらも合言葉を入れた人だけが見られる。
1. **マップ**：田野畑村のイラストマップに立てたピンをタップすると、その場所の説明と**最新の写真**が見られる。いまの活動を紹介する画面で、過去の写真は載せない。参考：https://platinumaps.jp/maps/morioka-city
2. **年表**：草創期から現在までを 1 本の縦の線でたどる。トップには **1 年につき写真 1 枚だけ**が並び、年を選ぶと、その年の春合宿・夏合宿・秋合宿・お祭り・その他の写真が見られる。過去の写真の保管場所。

**作らないもの**：管理画面（ブラウザからの追加・編集）、個別アカウント、コメントなどの双方向機能、検索、動画の再生、サムネイルの自前生成、多言語対応、アクセス解析。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 写真の管理 | **Google Drive のフォルダ階層がそのままデータになる**。「年 → 年_イベント名」のフォルダに写真を入れる（§4）。CSV やスプレッドシートでのタグ付けはしない |
| 写真の量 | 10,000 枚以上・100〜1,000 GB（動画を含む可能性あり）。写真は Drive に置いたまま、サイトからは Drive の画像 URL を直接参照する |
| 更新 | 初期の一括投入が中心。以後は私が Drive を整理し、再ビルドして反映する |
| 認証 | 共通の合言葉 1 つ。権限は閲覧のみ。**マップも年表も合言葉の内側** |
| Drive の共有 | アーカイブのフォルダごと「リンクを知っている全員」で共有する。フォルダを辿られる可能性は了承済み（§3.3）。写真の所有者についての懸念はない |
| ダウンロード | 原寸のダウンロードを許可（肖像権は解決済み） |
| 年表のトップ | **1 年につき写真 1 枚。イベント名・説明文・枚数は出さず、年と写真だけ**（§7.3） |
| 文章 | キャプションのみ。イベントの説明や年ごとの出来事は、年のページに後から足せるようにする（§4.5）。時代区分は後日共有 |
| マップ | ベースはイラスト画像（別途用意）。スポットは 20〜30 か所。村外の活動（早稲田祭・稲門祭・在京活動）はマップに載せず、年表の「その他」に入れる |
| 年表のカテゴリ | 春合宿／夏合宿／秋合宿／お祭り／その他（変わる可能性があるので設定ファイルで持つ）。「第○期」は表示しない |
| 文字の大きさ | **最小 20px**（サイト全体。例外はマップのピンの名前だけ） |
| デザイン | シンプル／森・自然。年表は参照デザイン（§8）の構成に合わせ、サイト全体もその質感に揃える。PC・スマホ両対応。日本語のみ |
| 費用 | 追加費用ゼロ（GitHub Pages 無料、Drive は既存契約、独自ドメインは保有済み） |

## 3. 構成

### 3.1 全体像
```
[Google Drive]  アーカイブ用フォルダ（年 → 年_イベント名）／ マップ用フォルダ（スポット名）
      │ Drive API（サービスアカウント、読み取りのみ。写真本体はダウンロードしない）
      ▼
[GitHub Actions]  pnpm ingest build → pnpm build → GitHub Pages へデプロイ
      │           （同じコマンドをローカルでも実行できる）
      ▼
[GitHub Pages]  静的サイト ＋ 合言葉で暗号化した一覧データ
      ▼
[ブラウザ]  合言葉で一覧を復号 → 写真は Drive の画像 URL を <img> で直接読む
```
サーバーは持たない。リポジトリに入るのはコードと設定だけで、**写真の一覧データはデプロイのたびに Drive から作り直す**（コミットしない）。

### 3.2 更新の流れ（運用時）
Drive でフォルダを整理する → GitHub の Actions 画面で「Run workflow」を押す → 数分で反映 → サイトの `/#/report` で取り込み結果（枚数と警告）を確認する。

### 3.3 了承済みの前提と限界（README にも書く）
- **合言葉が守るのは「写真の一覧」まで。** 一覧（Drive のファイル ID を含む）は暗号化して配るので、合言葉なしでは写真にたどり着けない。ただし Drive 側は「リンクを知っている全員」の共有なので、写真 1 枚の URL が外に出れば、その写真は合言葉なしで見られる。
- **フォルダごとの共有は了承済み。** アーカイブのフォルダ全体を「リンクを知っている全員」で共有する。写真 1 枚の ID が外に出ると、そこから親フォルダを辿って全体を見られる可能性があるが、これは受け入れる（イベント単位の共有などの対策は作らない）。
- 暗号化した一覧は誰でも取得できる場所に置くので、弱い合言葉は総当たりで破られる。合言葉は 12 文字以上を前提にする。
- Drive の画像 URL（`lh3.googleusercontent.com/d/…` など）は公式に保証されたものではなく、短時間に多数読み込むと 429 が返ることがある。まず M0 で実測する。
- GitHub Free で Pages を使えるのは公開リポジトリだけ。だからリポジトリにはデータを一切置かない。
- Safari は、そのサイトを 7 日ほど操作しないと保存した鍵を消すことがある。その場合は合言葉の再入力になる。

### 3.4 守ること
1. **リポジトリ、公開サイト、CI のログに、Drive のファイル ID・フォルダ ID、合言葉、サービスアカウントの鍵を平文で出さない。** 公開リポジトリの Actions ログは第三者も読める。
2. 2 つのルートフォルダの ID は秘密として扱う（これを知ればサイトを通らずに全写真を見られる）。置き場所は `.env` と GitHub Secrets だけ。
3. `.env` と鍵ファイルの中身を表示・要約・コミットしない。秘密の値は私が直接書き込む。
4. `public/data/` はビルドのたびに作る生成物。コミットしない。
5. 合言葉なしで見られるのは入口の画面だけ。マップも年表も、データを復号できたあとに描画する。
6. Drive の URL を組み立てるのは `photoUrl` モジュール 1 か所だけにする。URL の形が変わっても 1 ファイルの修正で済むように。
7. 合言葉はブラウザの外へ送らない（鍵の導出にだけ使う）。GitHub Pages はパスワードの送信のような機微なやり取りに使わないよう求めているので、この形を崩さない。
8. Drive に対しては読み取りだけを行う。

## 4. Drive のフォルダ規則

### 4.1 アーカイブ用フォルダ（年表のもとになる）
```
思惟の森アーカイブ/                 ← ルート（ID は秘密）
├─ 1968年/
│   ├─ 1968年_夏合宿/
│   └─ 1968年_秋合宿/
├─ 1990年/
│   ├─ 1990年_春合宿/
│   ├─ 1990年_夏合宿/
│   │    ├─ IMG_0001.jpg …
│   │    ├─ 表紙_集合写真.jpg      ← 名前が「表紙」で始まる写真が、年表のトップに出る 1 枚になる
│   │    ├─ オマルペ山/            ← 任意。スポット名と同じ名前なら、中の写真に場所が付く
│   │    └─ 1日目/                 ← それ以外のサブフォルダは、中身ごと「1990年 夏合宿」に入る
│   ├─ 1990年_菅窪祭り/
│   └─ 1990年_早稲田祭/
├─ 1970年代/                       ← 年代までしか分からない写真
│   └─ 1970年代_夏合宿/
├─ 年不明/
└─ _作業中/                        ← 名前が _ か . で始まるフォルダ・ファイルは読まない
```
推奨する形は `YYYY年/YYYY年_イベント名`。イベントフォルダの名前にも年を入れるのは、Drive の検索結果や移動ミスのときに、フォルダ単体で年が分かるようにするため。

### 4.2 読み取りルール
1. **正規化**：名前は Unicode の NFKC で正規化し、前後の空白を除き、連続する空白を 1 つにしてから解釈する（全角の数字や `＿`、Mac で作った名前の濁点の分離を吸収する）。
2. **年**：名前の先頭にある `YYYY年`、`YYYY年度`、`YYYY`（直後が区切り・名前の終わり・数字以外の文字。`1988夏` も可。数字が続く `19901` は年ではない）を年として読む。`YYYY年代` は年代、`年不明`・`年代不明` は不明。YYYY は 1950 〜 今年+1 の範囲だけを年とみなす（下限は設定値）。先頭が 4 桁の数字なのに年として読めない名前（`1975年代`、`3020年_未来` など）は警告を出し、年のないフォルダとして扱う。
3. **イベント名**：年のあとに続く文字列。区切りの `_`・`-`・空白は取り除く（区切りがなくてもよい）。
4. **写真の年**は、その写真から見て最も近い祖先フォルダに書かれた年。**写真のイベント**は、年が決まったあと最初に現れるイベント名（年付きフォルダのイベント名、または年フォルダの中にある年なしフォルダの名前）。イベントより深いフォルダの写真は、同じイベントにまとめる。ただし、深い側に年付きのイベント名（`1990年_秋合宿` など）が現れたら、そちらを採って警告する。
5. 年が決まる前に現れる「年のないフォルダ」は、ただの入れ物として通り抜ける（例：`スキャン分/1982年/1982年_夏合宿`）。年が決まらないまま置かれている写真は取り込まず、警告する。
6. 年フォルダの直下に置かれた写真は、イベント名なし（カテゴリ「その他」）で取り込む。年がはっきりしたフォルダ（`1990年` など）の直下なら、入れ忘れの可能性があるので警告する。年代・年不明のフォルダの直下は警告しない。
7. 同じ年・同じイベント名になったフォルダは 1 つのイベントにまとめる。
8. 親と子で年が食い違うときは、子の年を採って警告する。年代フォルダの中の年フォルダ（`1970年代/1975年`）は食い違いではない。
9. **カテゴリ**は `config/events.json` の規則を上から順に当て、最初に一致したものにする。どれにも当たらなければ「その他」。
   ```json
   { "categories": ["春合宿", "夏合宿", "秋合宿", "お祭り", "その他"],
     "rules": [
       { "includes": ["早稲田祭", "稲門祭"], "category": "その他" },
       { "includes": ["春合宿"], "category": "春合宿" },
       { "includes": ["夏合宿"], "category": "夏合宿" },
       { "includes": ["秋合宿"], "category": "秋合宿" },
       { "includes": ["祭", "まつり"], "category": "お祭り" },
       { "includes": ["春"], "category": "春合宿" },
       { "includes": ["夏"], "category": "夏合宿" },
       { "includes": ["秋"], "category": "秋合宿" }
     ],
     "fallback": "その他" }
   ```
10. **対象ファイル**は JPEG・PNG・HEIC/HEIF・WebP・GIF・TIFF・BMP（設定で変更可）。それ以外（動画、RAW、PDF など）は、種類ごとの件数をレポートに出すだけにする。ショートカットは取り込まず警告する。ゴミ箱の中は読まない。
11. 同じイベントの中に内容が同一の写真（`md5Checksum` が同じ）があれば、1 枚だけ残す（名前が `表紙` で始まるものがあれば、そちらを残す）。
12. **場所（任意）**：イベントの中のサブフォルダの名前が `config/spots.json` の `name` か `aliases` と一致したら、その中の写真に場所（`spot`）を付ける。一致しないサブフォルダの名前は使わない。
13. **表示順**：1 年の中は、カテゴリ順（`categories` の並び）→ イベント名順（`Intl.Collator('ja', { numeric: true })`）。イベントの中は、撮影日時（§5.2 で採用できたもの）の昇順で、採用できなかった写真はその後ろにファイル名の自然順で並べる。
14. **年の表紙**（年表のトップに出す 1 枚）：その年の写真を表示順に並べ、名前が `表紙` で始まる写真（正規化後）があればそれを、なければ最初の横位置の写真（幅 > 高さ）を、それもなければ最初の写真を表紙にする。`表紙` で始まる写真が複数あれば、表示順で最初のものを採って警告する。年代だけ分かる写真、年不明の写真も、それぞれのまとまりの中で同じように 1 枚を選ぶ。

このほか、Mac 由来の NFD で書かれた `1990年_プレイパーク` と NFC の同名フォルダが 1 つのイベントにまとまることもテストする。

年の表紙の選び方（その年の写真を表示順に並べたものと、表紙になる写真）：

| その年の写真（表示順） | 表紙 | 警告 |
|---|---|---|
| 縦、横、横 | 2 枚目 | — |
| 縦、縦 | 1 枚目 | — |
| 横、`表紙.jpg`（縦）、横 | 2 枚目 | — |
| 横、`表紙_a.jpg`（横）、`表紙_b.jpg`（横） | 2 枚目 | `MULTIPLE_COVERS` |
| 寸法不明、横 | 2 枚目 | — |
| 寸法不明、縦 | 1 枚目 | — |
| `裏表紙.jpg`（横）、横 | 1 枚目 | — |

表示順の例：春合宿に縦 1 枚、夏合宿に「撮影日時つきの縦、撮影日時つきの横、撮影日時なしの `IMG_2`・`IMG_10`」がある年は、春合宿の 1 枚 → 夏合宿の 4 枚（この順）→ お祭り → その他と並び、表紙は夏合宿の 2 枚目（最初の横位置）になる。

### 4.4 マップ用フォルダ
```
思惟の森マップ/                    ← アーカイブとは別のフォルダ
├─ 青鹿寮/                         ← 名前は config/spots.json の name（または aliases）と一致させる
├─ オマルペ山/
└─ …
```
- マップ用フォルダは、アーカイブ用フォルダの中に置かない（中に置くと、年のない写真として警告になる）。
- 各スポットのフォルダに、見せたい最新の写真を実ファイルで入れる（アーカイブから使うときはコピーする）。サブフォルダの中も同じスポットとして読む。
- 表示するのは、撮影日時の新しい順に最大 16 枚（撮影日時がなければ Drive への追加日時。枚数は設定値）。
- 一致するスポットがないフォルダ、ルート直下のファイル、ショートカットは取り込まず警告する。写真が 1 枚もないスポットは、説明だけのピンとして表示する。

### 4.5 Drive での操作とサイトへの反映

| やりたいこと | Drive での操作 |
|---|---|
| 写真を年表に載せる | その年・そのイベントのフォルダに入れる |
| 写真を外す | アーカイブの外へ移す。または `_` で始まるフォルダに入れる |
| 年やイベントを直す | フォルダを移動・改名する（ファイル ID は変わらない） |
| 年表のトップに出る 1 枚を選ぶ | その写真の名前を `表紙` で始まるものに変える（例：`表紙.jpg`。場所は動かさない） |
| 写真にキャプションを付ける | ファイルの「説明」欄に書く |
| イベントに説明文を付ける | イベントフォルダの「説明」欄に書く（年のページに出る） |
| その年の出来事を書く | 年フォルダの「説明」欄に書く（年のページに出る。年表のトップには出さない） |
| マップの写真を入れ替える | マップ用フォルダの中身を入れ替える |

どの操作も、再ビルド（§3.2）したときにサイトへ反映される。

### 4.6 警告コード

| コード | 意味と扱い |
|---|---|
| `NO_YEAR` | 年が決まらない場所に写真がある（取り込まない） |
| `NO_EVENT_FOLDER` | 年がはっきりしたフォルダの直下に写真がある（「その他」で取り込む） |
| `YEAR_MISMATCH` | 親と子で年が食い違う（子の年を採る） |
| `NESTED_EVENT` | イベントの中に、別のイベント名を持つ年付きフォルダがある（内側を採る） |
| `BAD_YEAR_NAME` | 先頭が 4 桁の数字だが年として読めない |
| `LOOKS_LIKE_COPY` | 名前の末尾が「のコピー」「(1)」など |
| `SHORTCUT` | ショートカット（取り込まない） |
| `DUPLICATE` | 同じイベント内の同一写真をまとめた |
| `MULTIPLE_COVERS` | 1 年の中に、名前が `表紙` で始まる写真が複数ある（表示順で最初のものを採る） |
| `UNKNOWN_SPOT`・`FILE_AT_MAP_ROOT`・`SPOT_WITHOUT_PHOTOS` | マップ用フォルダの問題 |

警告はフォルダ単位にまとめて件数を付ける。警告があってもビルドは止めない。

## 5. 取り込み（`scripts/ingest`）

### 5.1 Drive の読み方
- 認証はサービスアカウント。私が 2 つのルートフォルダをサービスアカウントに「閲覧者」で共有しておく。スコープは読み取り専用（`drive.metadata.readonly` で足りるかを M0 で確認し、足りなければ `drive.readonly`）。
- `files.list` をフォルダごとに呼ぶ：`q = "'<フォルダID>' in parents and trashed = false"`、`pageSize=1000`、`supportsAllDrives=true`、`includeItemsFromAllDrives=true`。1 ページの件数は指定より少ないことがあるので、`nextPageToken` がなくなるまで繰り返す。
- 取得する項目：`id, name, mimeType, description, size, md5Checksum, resourceKey, createdTime, imageMediaMetadata(width, height, rotation, time)`。
- `thumbnailLink` は使わない（数時間で失効し、Web ページから直接は使えないと公式に明記されている）。
- フォルダの走査は 4〜8 並列。429 と 5xx は指数バックオフで再試行する。1 万〜5 万ファイルを 5 分以内に読み終えること。
- ライブラリは `@googleapis/drive`（`googleapis` 全体は入れない）。

### 5.2 写真 1 枚ごとの扱い
- `imageMediaMetadata.time`（EXIF 形式 `YYYY:MM:DD HH:MM:SS`）は、**その年がフォルダの年と一致するときだけ**撮影日時として採用する。紙焼きのスキャンは、EXIF がスキャンした日になるため。採用した日時は並び順（§4.2 の 13）と、ビューアに出す月日に使う。
- 幅と高さは `imageMediaMetadata` から取る。`rotation` が奇数のときに入れ替えが必要かは、M0 で確かめて決める。取れない写真は 4:3 として枠を取り、読み込み後に直す。
- ファイル名はデータに含めない（個人名が入っていることがある）。`表紙` の判定は取り込みのときに済ませる。

### 5.3 コマンド
```
pnpm ingest build     # Drive を読む → §4 のルールで振り分け → public/data/ に暗号化して出力
pnpm ingest check     # 同じ処理をして、結果と警告を端末に詳しく表示する（ファイルは出力しない）
pnpm ingest verify    # 共有設定の確認：各年の表紙、各イベントから 1 枚、マップの全写真を、未ログインの状態で取得してみる
```
- `--from <file>` で、Drive の代わりに保存済みの一覧（JSON）を読めるようにする（フィクスチャと開発用。§10）。
- **失敗させる条件**：Drive API のエラー、取り込めた写真が 0 枚、`config/site.json` の `minPhotos` 未満。共有設定のミスなどで空のサイトを公開しないため。デプロイが失敗すれば、公開中のサイトは前の版のまま残る。
- **ログ**：`CI=true` のときは、件数と警告コード別の件数だけを出す。ID・名前・パスは出さず、例外メッセージも伏せる。詳細は暗号化したレポート（§7.6）とローカルの `check` で見る。

### 5.4 任意：フォルダの雛形づくり
1966 年〜今年の `YYYY年/YYYY年_{春合宿,夏合宿,秋合宿}` を一括で作る Google Apps Script を `tools/drive/create-folders.gs` として用意し、使い方を README に書く（既にあるフォルダは作らない）。写真が 1 枚もないイベントフォルダは、年のページに出さない。

## 6. データ形式

```ts
type YearKey = string;   // '1990' | '1970s'（年代だけ分かる）| 'unknown'（年代も分からない）
interface PhotoRef { id: string; rk?: string; w?: number; h?: number }   // id は Drive のファイル ID、rk は resourceKey
interface Photo extends PhotoRef { bytes?: number; mime: string; month?: number; day?: number; caption?: string; spot?: string }

// 年表のトップ用
interface YearEntry { yearKey: YearKey; count: number; cover?: PhotoRef; hasNote?: boolean }   // 写真のない年は count: 0 で cover なし
interface Index {
  v: number; builtAt: string;
  years: YearEntry[];                                   // 表示する順：1966, 1967, …, 1979, '1970s', 1980, …, 'unknown'
  eras: { name: string; from: number; to: number }[];   // config/eras.json から。空でよい
}

// 年のページ用
interface EventData { category: string; label: string; description?: string; photos: Photo[] }   // label が空ならカテゴリ名を見出しにする
interface YearData { yearKey: YearKey; note?: string; events: EventData[] }                       // note は年フォルダの「説明」

interface Spot { id: string; name: string; kana?: string; category: string; x: number; y: number; description: string; photos: Photo[] }   // x, y は画像に対する %
```
`years` には、写真か説明のあるいちばん古い年から、「写真のあるいちばん新しい年」と「今年」の遅いほうまでを、欠けなく入れる。Drive のフォルダ ID は、ファイル名にも URL にもデータにも入れない。

```
public/data/manifest.json     平文 { v, kdf: { salt, iterations }, builtAt }
public/data/check.bin         合言葉が合っているかの確認用
public/data/index.bin         Index（年表のトップは、これ 1 つで描ける）
public/data/y/{yearKey}.bin   YearData（年を開いたときに取得する）
public/data/spots.bin         { spots: Spot[] }
public/data/report.bin        取り込みレポート（§7.6）
```

**暗号化**
- 鍵：PBKDF2-HMAC-SHA256（反復 600,000 回、salt 16 バイト）で、合言葉から 256 ビットの鍵を作る。合言葉は NFKC で正規化し、前後の空白を除いてから UTF-8 にする（ビルド側とブラウザ側で同じ処理をする）。
- blob：`IV（12 バイト）| AES-256-GCM の暗号文 | 認証タグ（16 バイト）`。平文は **gzip した JSON**（暗号文には配信時の圧縮が効かないので、先に圧縮する）。Node の `crypto` は認証タグを別に返すので、暗号文の後ろに連結する（Web Crypto は連結した形を受け取る）。IV は blob ごとに乱数で作る。
- ブラウザ側は Web Crypto と `DecompressionStream('gzip')` を使う。ライブラリは要らない。
- salt・反復回数・版番号 `v` は `config/crypto.json` に固定で持つ（公開してよい値）。ビルドのたびに変えると、デプロイのたびに全員が合言葉を再入力することになる。合言葉を変えるときだけ、salt を作り直して `v` を上げる（`pnpm crypto:rotate`）。

試作での実測（12,711 枚・61 年分の仮データ）：index.bin は 2KB、年の blob は中央値 4KB（122 枚）・最大 23KB（669 枚）、1 年に 3,000 枚あっても 78KB、全体で約 460KB。Node で暗号化したものを Web Crypto で復号できること、合言葉の表記ゆれ（全角・前後の空白・NFD）でも同じ鍵になることは確認済み。

## 7. 画面仕様

URL は `/#/map`、`/#/timeline`、`/#/timeline/{yearKey}`、`/#/login`、`/#/report`。ルーターはハッシュ方式にする（GitHub Pages には SPA 用のフォールバックがないため）。

- `docs/reference/timeline-wireframe.html` が、年表のトップと年のページの配置・寸法の基準（写真は仮の絵）。
- `local/mock.html` はマップの操作感の参考。年表の部分は古いので使わない。マップとビューアについても、次の点はモックと違う：マップのパネルに年代の絞り込みはない（最新の写真だけ）／ビューアに「マップで見る」リンクはない／写真を白黒やセピアに加工しない／見た目は §8 に従う。

### 7.1 入口
- 起動時、保存済みの鍵（`localStorage` の `{ v, jwk, exp }`）で `check.bin` を復号できれば通す。できなければ `/#/login?next=…` へ。マップも年表も、この先にある。
- ログイン：合言葉 → 鍵を導出 → `check.bin` を復号。成功したら鍵を保存（30 日）して元の画面へ戻す。失敗は「合言葉が違います」とだけ出す。
- ログアウトで鍵を消す。
- 画面に置くのは、見出し「思惟の森の会 資料アーカイブ」、一言の説明、合言葉の入力欄、ボタンだけ。

### 7.2 マップ
- ベースは `public/map/` の画像（私が用意する。想定は幅 2,000〜3,000px）。画像のパス・実寸・最初に中心にする位置は `config/map.json` に持つ。
- 画像の上に、`config/spots.json` の位置（%）でピンを置く。ドラッグ・ホイール・ピンチで移動と拡大、＋−と全体表示のボタン、ダブルタップで拡大。拡大してもピンの大きさは変えない。
- 最初の表示は、スマホでは中心位置を少し拡大、PC ではほぼ全体。
- ピンをタップすると、PC では右側のパネル、スマホでは下からのシート（高さ 60〜90%）が開く。中身はカテゴリ、名前、かな、説明文、最新の写真（最大 16 枚）。写真をタップするとビューア（§7.5）。
- スポット一覧（PC は左のパネル、スマホは下部のシートを引き上げる）。カテゴリで絞り込める。項目をタップすると、その場所へ寄せてパネルを開く。
- ピンの下に出す名前だけは、文字の下限（20px）の例外にする（14px 以上）。ピンが 20〜30 個あり、重なりを避けるため。パネルや一覧の文字は 20px 以上。
- `/#/map?picker=1` では、画像をクリックした位置の x・y（%）と、`spots.json` に貼れる雛形を表示してコピーできる（20〜30 か所の座標入力用）。

### 7.3 年表のトップ（`/#/timeline`）
```
PC                                              スマホ
        年表                                    年表
                                                ●  昭和41年
  昭和41年  │                                   │  1966
     1966 ─●─  [   写真   ]                     │  [     写真     ]
           │                                    │
          1967        ← 写真のない年            ·  1967
           │                                    ●  昭和43年
  [  写真  ] ─●─  昭和43年                      │  1968
           │      1968                          │  [     写真     ]
```
- 見出し「年表」の下に、古い年から順に縦に並べる。
- **1 年につき写真は 1 枚（その年の表紙。§4.2 の 14）。文字は西暦と和暦だけ。** イベント名、説明文、枚数、キャプションは、この画面には出さない。
- 写真と年をまとめて 1 つのリンクにし、タップすると年のページ（§7.4）へ移る。
- **PC（幅 768px 以上）**：中央に細い縦線を引き、年ごとに線の上へ丸い点を置く。写真と年を線の左右に分け、1 年ごとに左右を入れ替える（写真のある年だけを数えて交互にする）。年は線のすぐ隣に寄せ、和暦（アクセント色の太字 20px）の下に西暦（太字 56px）。写真は 5:4 に切り抜いて角を丸める。行の高さは写真の高さで、行の間は 8px。
- **スマホ（幅 767px 以下）**：縦線を左端に寄せ、点を小さくする。点の右に和暦と西暦（太字 40px）、その下に写真を幅いっぱいに置く 1 列。
- 写真のない年は、薄い色の西暦（20px）だけを出す。PC では線の上に重ねて置き、スマホでは小さな点の右に置く。リンクにはしない。ただし年フォルダに説明がある年は、年のページへのリンクにする。
- 年代だけ分かる写真は、その年代の最後の年のあとに「年不明／1970年代」として、年代も分からない写真はいちばん下に「年不明／年代不明」として、年と同じ形（写真 1 枚）で並べる。
- 年代の索引（1960年代〜）を置く。PC では左に固定、幅 1099px 以下では上部に横並びで固定。タップでその年代へ移動し、いまの位置を示す。60 年分で PC 約 19,000px、スマホ約 23,000px の長さになるので欠かせない。
- 時代区分（`eras`）が入っていれば、その時代の最初の年の前に、時代の名前だけを置く。空でも壊れないこと。
- 表紙の画像は幅 800px のものを使い、画面に近づいた順に読み込みキュー（§9）へ入れる。index.bin を 1 回取れば、この画面全体が描ける。

### 7.4 年のページ（`/#/timeline/{yearKey}`）
- 上から順に、「← 年表」、和暦と西暦（太字 72px、スマホ 52px）、年フォルダの説明（あれば）、その年のイベントへ飛ぶボタンの列（イベントが 2 つ以上のとき。スクロールしても上部に残す）。
- イベントごとの区切り：見出し（イベント名。空ならカテゴリ名）、枚数、イベントフォルダの説明（あれば）、写真のグリッド（PC 4 列、幅 1099px 以下 3 列、スマホ 2 列。4:3 に切り抜いたタイル）。イベントと写真の並びは §4.2 の 13。
- 写真は 60 枚ずつ、スクロールに合わせて描画する（1 年に数百〜数千枚あっても固まらないこと）。
- 写真をタップするとビューア（§7.5）。
- いちばん下に、前の年・次の年へのリンク（写真か説明のある年へ）。
- 年表へ戻ったときは、開く前のスクロール位置に戻る。
- 年代だけ分かる写真（`1970s`）と年代不明（`unknown`）も同じ形で表示する。見出しは「1970年代」「年代不明」、和暦の位置には「年不明」。

### 7.5 ビューア
- 全画面で表示用（幅 1600px）の画像を出す。前後の移動（PC は ← →、スマホはスワイプ）、閉じる（Esc）。前後 1 枚ずつ先読みする。
- 年のページから開いたときは、その年の表示順で、イベントをまたいで前後に進む。マップから開いたときは、そのスポットの写真の中で進む。
- 開閉は履歴に積む（スマホの「戻る」で閉じる）。
- キャプション：`{年}年 {イベント名}`、月日が分かればそれも、スポット名、ファイルの説明。
- 「原寸をダウンロード」（サイズを表示。例：12.4 MB）と、「Drive で開く」。原寸の URL が警告ページを挟む大きさのときの案内文を用意する。
- 読み込みに失敗したら、予備の URL で 1 回だけ再試行し、だめなら灰色の枠と「Drive で開く」を出す。

### 7.6 取り込みレポート（`/#/report`）
取り込んだ日時、写真の枚数、年ごとのイベント一覧（イベント名・カテゴリ・枚数）、年ごとの表紙が指定（`表紙`）か自動か、警告（コード・フォルダのパス・件数）、対象外ファイルの種類別件数。フッターからリンクする。

### 7.7 共通
- ヘッダー：サイト名、「マップ」「年表」の 2 つのタブ、ログアウト。スマホでは 2 段にする（1 段目にサイト名、2 段目にタブとログアウト）。
- フッター：公式サイトへのリンク、問い合わせ先、最終更新日、取り込みレポート。
- 文言は日本語のみ、敬体で短く。空の状態やエラーは「何が起きて、次に何をすればいいか」を一文で伝える。

- スマホ：縦線が左端に寄り、点は小さく（12px 前後）なる。ラベルと見出しの下に写真が続く 1 列。

**取り入れるもの**は、この構成と質感（細い線、光る点、左右交互、角の丸い写真、「小さなラベル＋太い見出し」の組み合わせ、広い余白）。このサイトでは、ラベルを和暦、見出しを西暦に置き換え、本文は置かない（§7.3）。**持ち込まないもの**は、参照デザインの写真・文言・青い配色。

サイト全体の決まり：
- **色**：ページの地は #F8F9FB、内容の載る面は白。文字は #1A1A1A、補助の文字は #6B7280、罫線は #E5E7EB。アクセントは**深い緑 #2F5D3A の 1 色**（参照デザインの青の役割）で、点・ラベル・選択中のタブ・リンクなど「目印と操作できる場所」に使う。年表の縦線はその淡色（#CBD7CE）。
- **書体**：Noto Sans JP の Regular（400）と Bold（700）を自前で配信する（`@fontsource/noto-sans-jp`。文字の範囲ごとに分割されたファイルを使い、外部の CDN には頼らない）。
- **文字の大きさは最小 20px**（例外は §7.2 のピンの名前だけ）。本文 20px、行間 1.6 以上。見出しは太字で、ページの見出しと年表の西暦は 56px（スマホ 40px）、年のページの西暦は 72px（スマホ 52px）、イベントの見出しは 32px（スマホ 28px）。
- **写真**：角を丸める（年表の表紙は 20px、スマホ 14px。一覧のタイルは 12px）。枠と影は付けない。読み込み中は同じ比率の薄いグレー（#E5E7EB）。ホバーの効果は最小限。
- **装飾**：光彩は年表の点だけ。カードの影、グラデーション、装飾のためのアイコンは使わない。
- **余白**：8px の倍数。内容の面は最大幅 1,160px、スマホの左右は 16px。
- **動き**：操作への応答（パネルの開閉、ビューアの表示、索引からの移動）だけに 150〜250ms。読み込み時のフェードインや常時のアニメーションは入れない。`prefers-reduced-motion` を尊重する。
- 色を持つのは写真とマップの画像。まわりの UI は静かに保つ（余白を主役にする考え方は、当初の参考である nendo の Web サイトから引き継ぐ。書体の太さと角の丸みは、年表の参照デザインを優先する）。

寸法の出発点は `docs/reference/timeline-wireframe.html` の CSS（PC 幅 1280px で表紙 380×304px・点 40px、スマホ幅 390px で表紙 326×261px・点 12px）。

## 9. 非機能要件

- **画像の読み込み**：同時に 6 本まで（キューで制御し、`loading="lazy"` 任せにしない）。429 と通信エラーは 1 秒 → 3 秒 → 8 秒で再試行し、次に予備の URL、最後に灰色の枠にする。数値と URL の形は M0 の結果で決め、`config/site.json` に置く。
- **予算**：最初の画面に必要な JS は gzip 後 150KB 以内。index.bin は 12,000 枚相当のフィクスチャで 10KB 以内。画像の枠は先に確保し、読み込みで位置がずれないこと。フォントは `font-display: swap` にする。
- **対応環境**：直近 3 年のブラウザ（iOS Safari は 16.4 以降）。
- **アクセシビリティ**：ピン、年表の年、年のページの写真、ビューアはキーボードで操作できる。`focus-visible` を見せる。画像の `alt` はキャプション（なければ「{年}年 {イベント名}」。年表の表紙は「{年}年の写真を見る」）。コントラストは AA。
- **そのほか**：検索エンジンには載せない（`noindex`）。`<img>` には `referrerpolicy="no-referrer"`。CSP は `<meta>` で設定し（GitHub Pages では HTTP ヘッダーを足せない）、`img-src` は M0 で実際に画像が返ってきたホスト名に絞る。外部のフォント CDN と解析タグは使わない。

## 10. 検証の手段

1. **単体テスト（Vitest）**：§4.3 の表とツリーをそのままテストにする／カテゴリの規則／表示順と表紙の選び方／暗号の往復（Node で暗号化 → Web Crypto で復号。違う合言葉と改ざんは失敗する）／`photoUrl`。
2. **フィクスチャ**：`pnpm fixtures` で、Drive API の応答と同じ形の仮の一覧（§4.3 のツリー ＋ 12,000 枚相当。年の説明、イベントの説明、写真のない年、年代だけの写真を含める）と、ローカルの仮画像を作る。`pnpm ingest build --from fixtures/listing.json` と `VITE_PHOTO_SOURCE=local` で、Drive なしに全体が動く。
3. **E2E（Playwright、フィクスチャで実行）**：390×844 と 1280×800 の両方で走らせる。
   - 流れ：違う合言葉でエラー → 正しい合言葉で入る → マップのピン → パネル → ビューア／年表 → 年を選ぶ → 年のページ → ビューアの前後移動 → 戻る → 年表の元の位置に戻る → ログアウト。合言葉なしで `/#/map` と `/#/timeline` を開くと入口へ移ること。
   - 年表のトップ：画像の数が「写真のある年・年代・年不明のまとまり」の数と一致する（1 年 1 枚）。フィクスチャのイベント名・説明文が、この画面の文字に含まれない。
   - 文字の大きさ：どの画面でも、見えている文字の computed font-size が 20px 以上（マップのピンの名前を除く）。横方向のはみ出しがない。
   - axe で重大な違反が 0 件。
4. **見た目の確認**：年表のトップと年のページを両方の幅で撮り、同じ幅で撮った `docs/reference/timeline-wireframe.html` と並べる。配置・余白・文字の大きさの違いを列挙し、直すか、直さない理由を書く。
5. **`pnpm check:public`**：`dist/` に Drive の ID らしき文字列や平文の一覧が含まれていないこと、`public/data/`・`.env`・`local/` が Git の管理外であること、JS とデータが予算内であること。
6. **CI**：プルリクエストでは 1〜5 をフィクスチャで実行する（秘密の値は使わない）。`main` への push と手動実行では、実データで `ingest build` → ビルド → `check:public` → デプロイ。
7. スマホ実機での確認には HTTPS が要る（Web Crypto は安全なコンテキストでしか動かない）。LAN の IP アドレスに http でつないでも入口は動かないので、デプロイ先で確認する。
